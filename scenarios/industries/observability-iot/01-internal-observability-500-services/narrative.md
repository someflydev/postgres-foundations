# Internal observability for 500 services

The organization in this scenario is not trying to buy an architecture by slogan. It has a specific PostgreSQL decision to make under real operating constraints, and the right answer has to separate what belongs in core PostgreSQL now from what can wait until the workload proves it. The team has 12 engineers, medium operational tolerance, and a managed-service posture of mandatory. The largest table signals are metric_samples: 135,000,000, log_events: 78,000,000, service_catalog: 1,200. Peak read traffic is 1300 qps, writes are about 950 rows per second, and connection peaks reach 260.

The business context is deliberately uneven. Product leaders want a database plan that keeps the next release moving, while operations wants fewer unexplained moving parts. Some requirements are mature: the data shapes are relational_core, append_only_events, time_series_metrics, and the recurring workload patterns are append_heavy, analytics_adjacent, read_heavy. Other requirements are intentionally incomplete. The intake notes say: The team needs retention by service and day, BRIN-friendly time-window scans, and materialized rollups for dashboards. TimescaleDB is plausible later, but the first pain is disciplined core partitioning and owned retention jobs. This means an evaluator should not simply turn on every plausible extension. It should ask whether the recommendation removes a measured risk, improves correctness on a hot path, or merely introduces another operational surface area.

The schema discussion starts with core modeling. Relational state needs constraints before clever indexing. Append-heavy tables need retention windows, partition keys, and restore behavior before anyone reaches for automation. Search workloads need lexical behavior, permission filters, and freshness rules before semantic retrieval is treated as production-ready. Geospatial workloads need a clear distinction between coordinates that are displayed and spatial predicates that decide dispatch, pricing, compliance, or availability. Migration workloads need named ownership boundaries, validation reads, and rollback gates rather than permanent accidental federation.

The main review tension is timing. Several tools are credible in this domain, but credible does not mean immediate. pg_stat_statements is low-risk when the system has repeated traffic and someone owns review cadence. BRIN, btree, GiST, generated columns, RLS, logical replication, and materialized views should be evaluated as PostgreSQL capabilities before the answer moves to higher-burden extensions. Extensions such as PostGIS, TimescaleDB, pgvector, postgres_fdw, pg_partman, PgBouncer, and Citus need workload evidence and explicit runbooks. A good report names the triggers that would move a candidate from later to now.

The expected decision output should therefore read like a design review. Recommendations should include why the capability fits, why it is not a blanket endorsement, and what must be checked before production rollout. For this scenario, the strongest answers describe concrete next-stage triggers: query traces, EXPLAIN evidence, retention duration, compression goals, tenant or project scoping, pushdown verification, replication lag monitoring, restore drills, pool compatibility, or offline retrieval evaluation. Weak answers over-index on catalog labels and miss the operational cost.

There are also portability constraints. Managed PostgreSQL is part of the environment, so extension availability, version support, restore behavior, and major upgrade mechanics matter. If an extension is limited on a managed service, the report should say so directly and avoid hiding that cost behind convenience. If a feature can be built with core PostgreSQL and a small amount of disciplined maintenance, the conservative recommendation is often to stay core until the maintenance burden becomes observable.

Security and data ownership matter even in scenarios where they are not the headline. The intake names security constraints as none beyond normal operational controls. That should affect tenant filters, RLS posture, audit behavior, and retrieval design. It should not be used as a vague reason to add unrelated extensions. The learner should see that security posture narrows the design and increases the need for tests, but it does not excuse premature architecture.

The report should also be readable as a remediation artifact for a learner. It should make the boring work concrete: write the indexes that match the actual predicates, prove the retrieval or retention behavior with a representative fixture, and document the fallback when the advanced tool disappoints. If an extension is deferred, the report should not bury the reason in generic caution. It should say what evidence is missing, who must gather it, and which PostgreSQL-native baseline should be measured first. That style keeps the scenario useful both as a regression fixture and as a teaching case where operational judgment is the skill being practiced.

Use this scenario as a regression fixture and as a teaching case. A regression run should make sure the same recommendation classes appear as the rules evolve. A learner review should explain why each now, later, not-enough-evidence, or avoid-for-now outcome is justified by the intake rather than by fashion. The most important behavior is restraint: the report should make it easy to say yes to the boring PostgreSQL features that are due now, and equally easy to say not yet to tools whose trigger conditions have not arrived.
