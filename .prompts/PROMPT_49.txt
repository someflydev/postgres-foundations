PROMPT 49 — Top-level README, architecture docs, contribution guide
===================================================================

## Context

`postgres-foundations` now has a complete platform. This prompt
finalizes the **public-facing** documentation: the top-level README
(the first thing visitors see on GitHub), a consolidated architecture
overview, and a contribution guide.

Doctrine: the repo is a serious public artifact demonstrating
systems thinking. The top-level docs should match that bar — no
hype, no walls of emoji, no marketing copy. Be terse, specific, and
self-respecting.

## Prior work (verify before starting)

- All prior prompts complete.
- `README.md` has been a placeholder since PROMPT_01.
- `docs/architecture.md` has been authored and extended across
  several prompts; this prompt may touch it but should not
  rewrite it.

## Task

### 1. Top-level `README.md`

Rewrite. Target 800–1200 words. Sections:

- **Heading + tagline** — one sentence describing what this is.
  "A serious PostgreSQL learning and planning platform: structured
  curriculum, hands-on Docker lab, admin + extension mastery, and
  an explainable PostgreSQL architecture decision engine."
- **What's inside** — bullet list naming each subsystem
  (curriculum, lab, admin track, extension track, capstones,
  interview simulator, decision engine, scenario packs, prompt
  packs).
- **Who this is for** — self-learners, coaches, architects,
  teams doing PostgreSQL strategy.
- **Quickstart** — 10–12 lines of shell showing: clone, `uv
  sync`, `docker compose up -d pg`, `pgfound doctor`,
  `pgfound content seed ecommerce --phase 1`,
  `pgfound exercise run <id>`, `pgfound decision run <intake>`.
- **Directory map** — compact list of top-level directories with a
  one-line purpose.
- **Doctrine** — three short bullet lines (core first, "not yet",
  explainability). Link `docs/doctrine.md`.
- **Status and roadmap** — honestly frame what is in the repo
  today and link to the ADR directory for decision history.
- **How to use it** — three paths:
  - "I want to learn PostgreSQL from zero" → curriculum map.
  - "I want to level up operationally" → admin and extension
    tracks.
  - "I want to plan a PostgreSQL architecture" → decision engine.
- **License + attribution** — license statement (MIT unless
  otherwise specified — if unclear, leave placeholder and flag to
  the reviewer in the verification step of this prompt).

No emoji. No badges unless the project actually has CI producing
real statuses after PROMPT_50 — if badges are added, they link to
genuine artifacts (coverage, CI, PyPI if applicable).

### 3. Contribution guide

`CONTRIBUTING.md` at repo root. Sections:

- **How this repo thinks about contributions** — doctrine-aligned
  PRs only; no "add feature X because it's cool"; every PR cites
  a doctrine line or names a concrete learner/user need.
- **Authoring content** — point at `docs/authoring-lessons.md`
  and `docs/authoring-exercises.md`.
- **Authoring decision-engine content** — point at the 4-layer
  prompt pack and the catalogs/rules authoring guides.
- **Dev setup** — `uv sync`, `pre-commit install` (if configured
  in PROMPT_50), `make fmt`, `make lint`, `make test`.
- **Commit and PR hygiene** — imperative subject lines; scope
  prefixes (`feat(decision-engine):`, `fix(review):`); require a
  passing CI; require content validate + lint green.
- **Adding a new extension module** — a concrete checklist:
  update `curriculum/extensions/map.json`, the extension catalog
  entry, at least one rule, at least one scenario covering it,
  lessons under `lessons/extensions/`, exercises under
  `exercises/extensions/`, update the admin track cross-refs if
  operational, add a playbook under
  `docs/extension-track/`.
- **Adding a new industry or scenario** — a similar checklist.
- **Code of conduct** — short, firm statement; link out to a
  standard code-of-conduct file if used (`CODE_OF_CONDUCT.md`).
- **Reporting issues** — what to include.
