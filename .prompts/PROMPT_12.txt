PROMPT 12 — Phase 2: Relational joins and aggregation
=====================================================

## Context

`postgres-foundations`, Phase 2. Doctrine: introduce relational
structure (primary keys, foreign keys, one-to-many) and build the
learner's intuition for joins and aggregation. Keep exercises
bounded to 3–4 tables maximum. See `docs/doctrine.md` and the phase
2 entry of `curriculum/map.json`.

Phase 2 concepts: `primary_key`, `foreign_key`, `one_to_many`,
`inner_join`, `left_join`, `right_join`, `full_join`, `group_by`,
`aggregate` (`count`, `sum`, `avg`, `min`, `max`), `having`,
`distinct`, `count_distinct`.

Still **not yet** allowed: CTEs, window functions, lateral joins,
recursive queries, upserts, views, materialized views, subqueries used
for correlated logic (only trivial `IN (SELECT ...)` tolerated if a
lesson explicitly introduces it).

### 2. Lessons

Author at least **8 lessons** across these clusters. Sample coverage:

### 3. Exercises

Per lesson:

- 2 Level A (recognition: predict how many rows a join produces, or
  spot the missing GROUP BY column).
- 2 Level B (controlled production: write a query given table names).
- 2 Level C (independent production: oral defense required — "Why
  did you choose LEFT JOIN here?"; "What would break if I changed
  this to INNER JOIN?").
- 1 Level D (critique and repair: a JOIN that silently duplicates
  rows because of a many-to-many fan-out; a `GROUP BY` that misses a
  non-aggregated column; an incorrect `HAVING` vs `WHERE`).

Roughly 56 exercises.

Level D must include at least one "silently wrong aggregation" drill
where the query runs without error but the numbers are off due to
join fan-out. This is the single most common real-world bug this
phase prevents.

### 4. Domain-specific critique exercises

At least **three** Level D exercises should use domain scenarios drawn
from `docs/glossary.md` and real shapes:

- Ecommerce: a revenue query that double-counts due to joining orders
  × order_items × products without careful grouping.
- Scheduling: an "appointments per professional last week" query that
  loses professionals with zero appointments because it uses INNER
  JOIN instead of LEFT JOIN.
- SaaS: a "users per account" query where soft-missing data causes
  incorrect counts.
