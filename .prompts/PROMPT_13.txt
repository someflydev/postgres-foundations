PROMPT 13 — Phase 3: Schema design and database-enforced truth
==============================================================

## Context

`postgres-foundations`, Phase 3. Doctrine: the database enforces truth;
applications must not be the sole guardians of invariants. Normalization,
uniqueness, check constraints, defaults, nullability, reference tables,
`ALTER TABLE`, redesigning spreadsheet-shaped data into properly
modeled truth. See `docs/doctrine.md`, `curriculum/README.md`.

Phase 3 concepts: `primary_key` (as deliberate choice), `unique`
constraint, `not_null`, `check` constraint, `default`, `reference_table`
pattern, `normalization` (1NF, 2NF, 3NF), `denormalization` (when it is
a valid design choice), `alter_table`, `data_type_choice`, `surrogate_vs_natural_key`,
`enumerations`.

Still **not yet** allowed: JSONB, arrays, ranges, CTEs, window
functions, partitioning, indexing as performance tuning (beyond the
automatic index from a primary or unique key), transactions as a
subject of study (they are used, but not analyzed).

## Task

### 1. Extend domain packs to phase 3

Author `phase-03.sql` for `ecommerce`, `scheduling`,
`saas_multi_tenant`. These scripts add:

- Missing NOT NULL constraints that were deliberately omitted in
  phase 2 seeds for demo purposes.
- UNIQUE constraints where natural (email on customers, SKU on
  products, `(professional_id, starts_at)` on appointments — yes,
  introduce the idea of a composite unique constraint here).
- CHECK constraints: `quantity > 0` on `order_items`,
  `starts_at < ends_at` on appointments, `total_amount >= 0` on
  orders.
- Reference tables: `countries`, `currencies`, `appointment_statuses`
  as enum-table replacements for free-text columns from phase 2.
- At least one `ALTER TABLE` flow demonstrated in comments: "in phase
  2 we had X; in phase 3 we tightened to Y; here is how we would
  migrate".
- Idempotency still required — use `DO` blocks or `IF NOT EXISTS`
  where possible. Alternatively, for constraints that do not support
  `IF NOT EXISTS` in the target Postgres version, write a small
  `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN NULL; END
  $$` pattern.

### 2. Lessons

Phase 3 clusters:

- `why-the-database-enforces-truth`
- `picking-good-types`
- `uniqueness-and-identity`
- `check-constraints-and-defaults`
- `nullable-vs-not-null`
- `normalization-basics`
- `refactoring-spreadsheet-data`

Author **at least 10 lessons**. Required lessons (adjust cluster slugs
to match the map):

1. `why-the-database-is-the-source-of-truth` — application-level checks
   are insufficient; two apps will disagree; constraints outlive code.
2. `picking-good-types` — `text` vs `varchar`, `numeric` vs `float`,
   `timestamptz` vs `timestamp`, `boolean` vs `int`; *why* Postgres
   prefers `text`.
3. `primary-keys-that-make-sense` — surrogate vs natural; UUIDs are
   introduced briefly but deferred to phase 4; emphasize `bigint
   identity` now.
4. `uniqueness-beyond-primary-key` — single and composite UNIQUE
   constraints; the automatic index; uniqueness under NULLs.
5. `check-constraints` — check constraints as invariant declarations;
   multi-column checks.
6. `not-null-vs-nullable` — when `NULL` is a legitimate signal vs a
   design smell; impact on queries and aggregates.
7. `defaults-and-generated-columns` — `DEFAULT`, `GENERATED ALWAYS AS
   IDENTITY`, stored generated columns (don't go deep yet).
8. `reference-tables-over-free-text`
9. `normalization-1nf-2nf-3nf` — concrete examples; why 3NF is usually
   the target.
10. `refactoring-spreadsheet-shape-to-relational` — a full worked
    example starting from a denormalized table and ending with a
    properly modeled schema.

### 3. Exercises

Per lesson: A/B/C/D as before. Approximately 65–70 exercises total.

Focus emphases:

- Level B and C exercises dominated by **ALTER TABLE** work — adding
  constraints to existing tables, tightening types, migrating legacy
  columns.
- Level D exercises are the heart of this phase: given a real
  lurking-bug schema, diagnose what invariants are missing and
  propose the ALTER TABLE statements. Require the learner to state
  the concrete incident that could arise without the constraint
  ("without a CHECK on quantity, negative inventory becomes possible
  during refund processing").
- At least **one** Level D exercise uses a real-world-flavored
  spreadsheet-to-relational migration scenario (with a CSV file in
  `seed-data/packs/ecommerce/fixtures/spreadsheet-legacy.csv`).
