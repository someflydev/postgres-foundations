# Geo Logistics Reference Writeup

## Modeling

The model separates durable facts from dispatch computation. Couriers have a current point, vehicles describe capacity, service zones carry polygons, deliveries capture SLA state, and breadcrumbs preserve historical movement. The dispatch algorithm can read these facts but its scoring rules are not hidden inside database triggers.

## Partitioning

Breadcrumbs are partitioned by recorded time because replay, retention, and ingest all align with time windows. At roughly one hundred million rows each year, monthly partitions keep maintenance bounded while avoiding a daily partition count that creates catalog noise. pg_partman should create future partitions and detach old partitions after export.

## Indexes

GiST indexes support zone polygons, current courier points, and breadcrumb points. Btree indexes support region and status filters, delivery SLA reports, and courier-time replay. Delivery notes use a generated tsvector and a GIN index so keyword search stays in PostgreSQL core.

## Operations

The first triage tool is pg_stat_statements. Operators compare total time, mean time, calls, rows, and plan drift for the zone top-N, SLA, replay, and note-search queries. Partition maintenance is checked before month boundaries, and retention is a detach-and-export process rather than a large delete.

## Extension posture

PostGIS is a now decision because the platform stores real service-zone polygons and GPS points, and the critical questions require geometric predicates such as containment and proximity. A plain latitude and longitude pair with numeric comparisons can approximate bounding boxes, but it cannot correctly answer whether a courier is inside an irregular zone, cannot express future geography-aware distance checks cleanly, and would push correctness into application code. The operational burden is accepted because PostGIS is mature, widely available in managed PostgreSQL offerings, and directly tied to the product's data model.

pg_partman is also a now decision. PostgreSQL core partitioning is the underlying mechanism, but pg_partman removes routine partition creation and retention toil for a table that grows continuously. The measurable signal is the breadcrumb volume: about one hundred million rows per year with replay queries that always include recorded_at. The rollback path is straightforward because child partitions remain ordinary PostgreSQL partitions.

Core full-text search is now for delivery notes. The notes are short operational text: gate codes, damaged package notes, customer instructions, and driver comments. The required behavior is keyword retrieval, ranking, and explainable filtering. That makes generated tsvector plus GIN the right first design.

pgvector is avoid for now. There is no requirement to find deliveries conceptually related to a vague prompt, no evidence that keyword search fails, and no owner for embedding refresh, model drift, or vector index rebuilds. The trigger to reconsider would be measured search sessions where exact and fuzzy lexical search cannot recover the relevant delivery notes and support teams can name a semantic use case with latency and freshness requirements.

TimescaleDB and Citus are later or avoid decisions. TimescaleDB might become relevant if downsampling, compression, or time-series policy automation becomes more important than portability. Citus would need a cross-region scale problem and a defensible distribution key. Neither signal exists for a regional platform at the stated scale.

## Not yet

Do not add semantic retrieval, distributed PostgreSQL, or a database-resident dispatch optimizer. Add them only when pg_stat_statements, support tickets, and product requirements show the core design is no longer sufficient.

## Detailed defense

The central design choice is to keep PostgreSQL responsible for facts, integrity, and inspectable access paths while leaving live dispatch scoring outside the database. That boundary matters because it keeps the schema stable even if the dispatch team changes weights, routing vendors, or machine-learning experiments. The database records couriers, vehicles, zones, deliveries, breadcrumbs, and SLA outcomes. It can answer whether a courier was inside a zone, which delivery missed its promise, or which breadcrumb sequence explains a support complaint. It should not become the place where unversioned dispatch heuristics are hidden in triggers or stored procedures.

Couriers are modeled with region, status, last seen time, and current location because the top-N query needs to filter before it ranks. The status column is intentionally constrained to a small set of states. At this scale, vague state names become operational debt: support staff need to know whether a courier is offline, available, or assigned without decoding application-specific flags. Vehicles are separate because capacity and identity are vehicle facts rather than courier facts. A courier may change vehicles, and vehicle capacity can affect dispatch eligibility even though the actual algorithm is off-platform.

Service zones use polygons rather than administrative labels because the product requirement is spatial. A zone name alone cannot answer whether a breadcrumb or current courier point is inside the service boundary. A bounding box can reduce candidates, but it is not the business rule. PostGIS lets the system express the rule in the database with a GiST index and a predicate that reviewers can inspect. The zone table also carries an active flag so retiring a zone is an ordinary data change rather than a destructive schema event.

Deliveries carry requested, promised, delivered, and status fields so SLA reporting is derived from auditable timestamps. The schema does not store only a precomputed on-time flag because the definition of on-time may change by customer, product, or reporting window. Keeping the underlying timestamps supports corrections and makes the SLA query reviewable. The delivery note column is ordinary operational text. It is indexed with a generated tsvector so support can find "gate code", "missing package", or "damaged box" without introducing a separate document system.

Breadcrumbs are the only table expected to grow into very large volume. The estimated rate, roughly one hundred million rows per year, is enough to make retention and maintenance design necessary, but not enough to force distributed PostgreSQL. Range partitioning by recorded_at matches every required maintenance and replay path. Replay queries are time-windowed, incident investigations start with a day or hour, and retention is age-based. Monthly partitions keep the partition count low while still allowing detach and archive operations to finish without touching the whole table. If ingest or replay patterns later show that a month is too large, the progression path is to move to weekly or daily partitions, not to abandon the core design.

pg_partman is justified as an automation layer over core partitioning. The table remains a PostgreSQL partitioned table, so the exit path is visible and portable. The team uses pg_partman to create future partitions, check that the current insert target exists, and detach partitions after the cold archive process succeeds. This avoids an operational pattern where a human has to remember to create the next partition during a month-end incident. The runbook should include a scheduled check before the boundary, a verification query for orphaned or default-partition rows if a default partition is added later, and a rollback note for failed detach or archive steps.

The index set is deliberately small. The courier region-status-last-seen index supports filtering available couriers in a region before ordering by recency. The courier and zone GiST indexes support spatial predicates. The delivery zone-requested index supports SLA reporting by zone and time. The breadcrumb courier-time index supports replay for one courier over a window, and the breadcrumb GiST index supports spatial investigations when support starts from an area rather than an identifier. The delivery note GIN index supports lexical search. Additional indexes should be justified by pg_stat_statements and EXPLAIN, not by guessing.

Spatial queries need careful operator choice. `ST_Contains` is correct for asking whether a point lies inside a polygon, but edge cases matter. If the business considers a courier exactly on a boundary eligible, the query may need `ST_Covers` instead. That is a business rule, not a database limitation. The design should document which interpretation dispatch expects and should include examples for boundary points. The schema uses SRID 4326 for storage because the source data is GPS-like longitude and latitude. If distance ranking becomes central, the team can add geography casts or projected working columns for specific regions, but that should be driven by measured query plans and correctness tests.

SLA reporting should aggregate from deliveries rather than breadcrumbs. Breadcrumb data can explain why something happened, but delivery timestamps are the contractual source of truth. A slow SLA report should first be triaged with `pg_stat_statements`: total time identifies the highest-cost query family, mean time identifies outliers, calls identify dashboard loops, and rows identify whether a query is scanning more than expected. If SLA reports become a dashboard hot path, the next core step is a rollup table or materialized view with a freshness contract. That is still a core PostgreSQL choice and should precede any distributed or analytics extension.

The breadcrumb replay query must always include courier_id and a bounded recorded_at range. A replay endpoint that allows open-ended scans is an application bug. The runbook should document acceptable windows, maximum row counts, and the support escalation path when a replay needs a longer history. For large investigations, an operator can run a batch job against a detached or read-only copy rather than burdening the primary operational database. This posture protects ingest and dispatch reads during incidents.

Operationally, the first dashboard is not a map. It is a set of database health questions. Are inserts keeping up with current breadcrumb volume? Are partitions being created before writes arrive? Are GiST indexes growing unexpectedly after zone changes? Are autovacuum settings keeping up with update-heavy courier current locations? Are the same note-search queries being run repeatedly by support tooling? `pg_stat_statements`, relation size checks, autovacuum observations, and partition catalogs answer these questions before the team changes architecture.

PostGIS adds operational burden but solves a real correctness problem. The team must know how to restore a database with PostGIS installed, how to test extension availability in managed environments, and how to handle upgrades. Those costs are acceptable because the alternative is reimplementing geometry in the application or making incorrect approximations. The portability story is also reasonable: PostGIS is available in many managed PostgreSQL services and is a common dependency for logistics systems. The writeup should still name the hosting assumption and test restore drills in the actual target environment.

pg_partman adds a narrower burden. It needs extension availability, background or scheduled maintenance, and ownership of retention policy. It does not change the data model into a proprietary shape. The primary fallback is manual partition creation and detach SQL. That fallback should be documented so a failed pg_partman job does not block ingest. The team should also monitor for partitions that are missing expected indexes, because a newly created child without the right access path can create a sudden performance regression.

pgvector remains unjustified because the retrieval problem is not conceptual. A support user looking for a delivery note usually has a concrete phrase, customer instruction, address fragment, or exception term. Full-text search handles that directly and explainably. Semantic retrieval would introduce embeddings, model versioning, index rebuilds, privacy review, and relevance evaluation without a named user workflow. If future support tickets show that agents ask questions like "find deliveries with access problems similar to this one" and lexical search cannot recover the right notes, then pgvector can be revisited with a proper benchmark and owner.

TimescaleDB is also not a first move. Breadcrumbs are time-series-like, but the required operations are partitioned ingest, bounded replay, and retention. Core partitioning plus pg_partman covers those needs. TimescaleDB might become attractive if compression, continuous aggregates, or time-bucket query ergonomics become decisive. The trigger should be specific: storage cost from cold breadcrumbs exceeds the agreed budget, rollup maintenance becomes unreliable, or query complexity around time buckets creates repeated defects. Until then, adding TimescaleDB would reduce portability and increase operational surface without solving a current pain.

Citus should be avoided at this stage. A regional platform with 10,000 to 20,000 deliveries per day and 1,000 to 2,000 couriers does not need distributed PostgreSQL for the relational core. A region_id distribution key might look plausible, but dispatch and support queries can cross zones and time windows, and the system has not exhausted single-node PostgreSQL. Citus would require shard management, co-location planning, distributed query awareness, backup and restore changes, and a stronger operations team. The correct progression is to prove the single-node design with partitions, indexes, and read replicas before considering distribution.

Security is intentionally light in this reference because the prompt focuses on extension posture, but region-scoped RLS is still useful. If multiple regional teams share the same database, `current_setting('app.region_id', true)` gives the application a clear way to set access context. In production, that must be paired with role design, connection-pool hygiene, tests that prove missing settings fail closed where appropriate, and administrative paths for cross-region support. If the platform later becomes multi-tenant across independent customers, the RLS model needs to become stricter.

The solution should be evaluated by its change posture as much as its first schema. Adding a zone should be a data operation. Adding a new delivery status should require a conscious migration. Changing partition granularity should have a migration plan. Adding semantic search, TimescaleDB, or Citus should require measured signals and a rollback plan. This is the core-first doctrine in practice: adopt PostGIS because correctness demands it, use pg_partman because partition operations are predictable, keep FTS in core because it fits the text problem, and defer everything else until the workload proves the burden is worth carrying.

## Reviewer checklist

A reviewer should first test whether the design answers the three operational questions the business will actually ask. Where are eligible couriers now? Which deliveries missed their promise and why? What path did a courier take during a disputed window? If the schema or queries cannot answer those questions without hand-waving, the design is incomplete even if the extension list looks impressive.

The second review point is write amplification. Breadcrumb inserts are continuous, courier current locations may update frequently, and delivery state changes during fulfillment. Every extra index on those tables has a cost. The reference index set should be treated as a starting set, not a permanent maximum. If a learner adds many expression or JSON indexes, ask for the pg_stat_statements evidence and the specific query they support. If they remove the courier-time breadcrumb index, ask how replay stays bounded.

The third review point is spatial correctness. The learner should name SRID, predicate choice, and boundary behavior. Logistics systems often have edge cases around airports, campuses, gated communities, or overlapping service zones. A good answer does not need to solve every future geography issue, but it should not pretend that latitude and longitude columns plus a btree index are equivalent to PostGIS geometry.

The fourth review point is retention. A partition plan without a detach, archive, and restore story is only half a plan. Ask how operators know the next partition exists, how they recover if a partition was missed, how old data is exported, and how a support case can access cold breadcrumbs. The answer should keep raw deletes out of the hot path.

Finally, test the extension posture against burden. PostGIS and pg_partman are justified now because they remove correctness and maintenance risks. pgvector, TimescaleDB, and Citus are not justified by the stated workload. A strong learner answer makes those distinctions calmly and gives measurable triggers for changing them later.
